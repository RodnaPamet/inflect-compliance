# 2026-11-12 — Capacity budget C1: limits on every container, OrangeHRM lab retired

**Commit:** see the `claude/capacity-c1` branch (`feat(deploy): capacity budget C1 …`).

## Design

The capacity budget (master roadmap § Capacity budget, rule G5) asks four things
of the production VM:

1. every container has a memory limit and a CPU cap;
2. the memory limits together stay at or under host memory minus 1.5 GB
   (14.5 GB = 14,848 MiB);
3. batch-shaped services are capped at 1.0 CPU, so the request path keeps a core;
4. the request path (app, caddy, pgbouncer, postgres, redis) gets caps that
   never starve it on 2 vCPUs.

Before C1 no service declared a limit. C1 adds `mem_limit` + `cpus` to every
service in `deploy/docker-compose.prod.yml` and in the two overlays that run on
the VM (`docker-compose.harness-scanner.yml`, `docker-compose.legacy-mcp-proving.yml`),
and retires the OrangeHRM lab (owner decision 2026-11-12) from the
repo-canonical deploy set: its overlay and its two Caddy vhosts leave the
repository here, and its three containers and two public vhosts leave the
running VM when the operator runs runbook steps 1–2 below. Merging this commit
changes nothing on the VM by itself.

`mem_limit` / `cpus` (and `cpu_shares`) are the service-level Compose keys. The
stack runs under plain `docker compose`, not swarm, so `deploy.resources` is the
wrong form; these are also the keys this repository used before (the
observability stack's caps, #603).

### C1 — the limits

The rule for services other than `app` and `worker`: about 1.5x the measured
peak, rounded up, with a floor (128 MiB for a small native process, 256 MiB for
a Node process). Where a service's own mechanics need more than that, the
mechanics win, and the row says which.

| Service | File | `mem_limit` | Basis | `cpus` | `cpu_shares` |
| --- | --- | ---: | --- | ---: | ---: |
| app | prod | 1536m | **PROVISIONAL** (owner decision): 1.5 GB until re-measured; V8 heap stated at 1024 (below) | 1.5 | — |
| worker | prod | 1536m | **PROVISIONAL** (owner decision): 1.5 GB until re-measured; V8 heap stated at 1024 (below) | 1.0 | 512 |
| clamav | prod | 3072m | reload: 2 × 964 anon ≈ 1.9 GiB, plus page cache (below) | 1.0 | 512 |
| postgres | prod | 2048m | 1.5x is 609; a database floor, because the limit counts page cache | 1.5 | — |
| redis | prod | 768m | 2 × `--maxmemory 256mb` for an AOF-rewrite fork, plus the process | 1.0 | — |
| caddy | prod | 256m | 1.5x is 111; floor with room for TLS caches and ACME | 1.0 | — |
| watchtower | prod | 128m | 1.5x is 59; floor | 0.25 | — |
| pgbouncer | prod | 128m | 1.5x is 24; floor | 1.0 | — |
| harness-scanner | scanner overlay | 512m | 1.5x is 233; room for a larger estate's code parse | 1.0 | 512 |
| harness-egress | scanner overlay | 256m | 1.5x is 99; Node floor | 0.5 | — |
| legacy-mcp-proving | proving overlay | 256m | 1.5x is 134; Node floor | 0.5 | — |
| **Total** | | **10,496 MiB** | budget 14,848 MiB; ~4.25 GiB unallocated | | |

The total also fits the *measured* host memory minus 1.5 GB
(16,003 − 1,536 = 14,467 MiB), which is the stricter reading of the rule.

**The V8 heap ceiling moves with `mem_limit`, so `app` and `worker` state it.**
The runtime image sets no `NODE_OPTIONS` (the Dockerfile's
`--max-old-space-size=8192` is in the builder stage only), and with no flag
Node sizes its default old space from the cgroup limit
(`uv_get_constrained_memory`). Measured on Node 22 with `NODE_OPTIONS` unset:
`heap_size_limit` 2096 MiB with no memory limit, 792 MiB inside a 1536 MiB
cgroup (`process.constrainedMemory()` 1536). Unstated, the limit would have cut
the heap ceiling to about half of itself, and a heap overrun ends in
`FATAL ERROR: Reached heap limit` and exit 134 — a V8 abort, not a cgroup OOM
kill, so `memory.events` `oom_kill`, `/proc/vmstat` `oom_kill` and
`State.OOMKilled` all stay clean. Both services therefore carry
`NODE_OPTIONS: "--max-old-space-size=1024"` in `environment:` (heap limit
1048 MiB measured under the same cgroup): above the ~790 MiB default and
leaving ~500 MiB of the limit for buffers, code and native memory, which the
flag does not bound. `environment:` overrides `env_file:`, so a
`NODE_OPTIONS` in `.env.prod` stops applying to these two services — runbook
step 3 counts whether one exists. The guard holds the pair: the stated heap
must sit above half of `mem_limit` and at or below three quarters of it, so
changing one without the other fails CI. The overlays' Node services are left
on the default: at a 256m or 512m limit Node's floor gives a ~259 MiB heap,
above their measured peaks, and a heap abort there is a fixture restarting.

**ClamAV and the signature reload.** The repository supplies no `clamd.conf`,
so the `clamav/clamav:1.4` image's default applies, and in it
`ConcurrentDatabaseReload` is on: when freshclam brings new signatures, clamd
builds the new engine BESIDE the old one and swaps, so anonymous memory roughly
doubles for the length of the reload. The loaded engine was 964 MiB anonymous at
the snapshot; a reload therefore needs about 1.9 GiB of anonymous memory, and
the measured peak's ~1.1 GiB of page cache sits on top (reclaimable, but it is
charged to the cgroup). 3 GiB covers both and is ~1.45x the measured peak.
Turning concurrent reload off would halve the need, but clamd then refuses scans
for the length of every reload (several times a day), which trades memory for
upload availability; not done.

### CPU caps on 2 vCPUs

A `cpus` cap is a CFS quota: it limits what a container may use, it reserves
nothing. A cap at or above what a service can use restricts nothing, and a cap
on the request path below what it needs adds latency to every request while the
CPU may be idle. So:

- **Request path, capped to stop one member starving the others, never below
  what it can use.** `app` 1.5: Next.js runs JavaScript on one thread, so 1.5
  lets GC and the libuv pool burst while guaranteeing the rest of the request
  path half a core if a render loop spins. `postgres` 1.5: a runaway query
  cannot take both cores from `app`. `pgbouncer` and `redis` 1.0: both run a
  single-threaded loop, so the cap states the ceiling they already have.
  `caddy` 1.0: TLS termination at this load is far below a core.
- **Batch-shaped, 1.0 CPU and half the weight.** `clamav`, `worker` and
  `harness-scanner`. The 1.0 quota is the rule; `cpu_shares: 512` (cgroup v2
  `cpu.weight` ~50 against the default ~100) is what makes "the request path
  keeps a core" hold when several batch services run at once — three 1.0
  quotas can still sum to more than the host, but under contention the request
  path gets twice their share.
- **Small and idle.** `watchtower` 0.25, `harness-egress` and
  `legacy-mcp-proving` 0.5.

`orangehrm-mcp`, 449 MiB at peak together, plus a public PHP application) is a

  baseline: no file references them any more.

## Decisions

- **Provisional app/worker limits.** The owner chose 1.5 GB each now rather than
  wait for a measurement: an unlimited container is the larger risk. They are
  ~2.6x and ~3.6x the 24-minute peaks, but those peaks hold none of the
  02:00–05:30 UTC chain (identity sync, HRIS sync, the JML passes, the
  data-lifecycle purge, evidence and narrative jobs).
- **Postgres gets more than 1.5x.** A cgroup limit charges page cache, and
  Postgres relies on the OS cache for reads, so a tight limit would turn cache
  hits into disk reads before it ever OOM-killed anything.
- **The guard's population is the canonical file plus the two running
  overlays.** `docker-compose.pipelock.yml` is not enabled and carries no
  limits; they are owed when it is enabled, and the guard names it as outside.
- **The budget's ledger in `docs/ai-architecture-roadmap.md` is not edited
  here.** Its capacity-budget section still describes the stack as unlimited
  and unmeasured. A separate pull request is rewriting that file, so editing it
  here would conflict with that rewrite. The ledger's "Today's stack" line (the
  per-service limits, the 10,496 MiB allocated, the C0 peaks) is owed in that
  pull request, or in the first one after it merges, and takes its figures from
  the tables above.
- **`app` and `worker` state their V8 heap ceiling.** A memory limit moves
  Node's default heap ceiling. Stating `--max-old-space-size` keeps that
  ceiling a decision in this file, not a side effect of `mem_limit`. See
  "The V8 heap ceiling" above.
- **The lab's teardown uses `rm --stop`, not `down`.** See the runbook.

## Operator runbook (run once, after the merge)

Two ways to run it (owner decision 2026-11-12). **Option 2, the durable one:**
dispatch the `VM apply` workflow from `main` with the action each step names
(`VM apply → <action>`); the owner approves each run in the `production`
environment, and no session holds a credential. Every write action runs its
preflight first in the same run. **Option 1:** from a checkout of the merged
commit, with `gcloud` signed in by the owner. In a Claude Code cloud session
prefix each `gcloud` and `deploy/apply.sh` with
`env -u CLOUDSDK_AUTH_ACCESS_TOKEN`. `SSH` below stands for
`gcloud compute ssh inflect-compliance --zone europe-west1-b --tunnel-through-iap --command`.
No step prints a secret; never `cat` an env file or the live compose file.

| Step | `VM apply` action (Option 2) |
| --- | --- |
| 1 | `retire-lab-containers` |
| 2 | `retire-lab-vhosts-preflight`, then `retire-lab-vhosts` |
| 3 | `preflight` (reports the `NODE_OPTIONS` count in `.env.prod` and warns if it is not 0), then `apply` |
| 4 | the `Scanner VM` workflow, as below |
| 5 | `recreate-legacy-mcp-proving` |
| 6 | the `VM capacity` and `VM check` workflows, as below |
| 7 | in the product, as below |

**1. Stop and remove the lab's containers, keeping its volumes** (no service
window needed; `VM apply → retire-lab-containers` does all of this, by label
when the VM has no copy of the overlay):

```bash
SSH "sudo docker ps -a --format '{{.Names}}' | grep orangehrm"
SSH "cd /opt/inflect && sudo docker compose --env-file .env --env-file .env.prod \
  -f docker-compose.prod.yml -f docker-compose.orangehrm-lab.yml \
  rm --stop --force orangehrm-mcp orangehrm orangehrm-db"
SSH "sudo docker ps -a --format '{{.Names}}' | grep -c orangehrm || true"   # expect 0
SSH "sudo docker volume ls --format '{{.Name}}' | grep orangehrm"           # both volumes remain
```

Why `rm --stop` and not `docker compose -f <overlay> down`: the lab runs in the
production Compose project (`inflect`). `down` also removes the project's
networks, starting with `inflect_default`, which every production container is
attached to; and with `docker-compose.prod.yml` in the `-f` list it stops the
whole production stack. `rm --stop` acts on the three named services only and
never removes a named volume. If the VM has no copy of the overlay, remove the
containers by the names the first command printed:
`SSH "sudo docker rm -f <name> <name> <name>"`.

## Rollback plan

- **The limits.** Revert the commit (a PR), merge, then `CONFIRM=1 deploy/apply.sh`
  and steps 4–5 for the overlays. In an incident, faster: every apply keeps
  `/opt/inflect/docker-compose.prod.yml.bak.<timestamp>` and prints the exact
  rollback command at the end of its run; running it — or `VM apply →
  rollback-preflight`, then `rollback`, which restores the newest backup —
  restores the previous file and recreates without limits (repo and VM then drift until the revert merges,
  which `check-drift.sh` reports).
- **One limit too tight, mid-incident:**
  `SSH "sudo docker update --memory 2g --memory-swap 2g inflect-<service>-1"`
  raises a running container's limit without recreating it. It lasts until the
  container is next recreated, so follow it with a PR raising `mem_limit`. For
  `app` and `worker` it does NOT raise the V8 heap ceiling: that is fixed when
  Node starts, from `--max-old-space-size`. If the signal is a heap abort
  (below), the fix is a PR raising `mem_limit` and the stated heap together,
  then `CONFIRM=1 deploy/apply.sh`, which recreates the container.
- **The lab.** Within 30 days, while its volumes exist: restore the overlay and
  the two vhosts from the parent of this commit
  (`git show <commit>^:deploy/docker-compose.orangehrm-lab.yml`, and the
  Caddyfile blocks), push the vhosts with `CADDY_ONLY=1 CONFIRM=1 deploy/apply.sh`,
  then `docker compose --env-file .env --env-file .env.prod -f docker-compose.prod.yml
  -f docker-compose.orangehrm-lab.yml up -d` on the VM — it re-attaches the kept
  volumes. It needs limits of its own to stay inside the budget (449 MiB peak;
  the budget has ~4 GiB unallocated). After the volumes are removed, the
  installer has to be run again (the overlay's history describes the sequence).

## Risk assessment

**An OOM kill at a limit.** The kernel kills the container's largest process;
`restart: unless-stopped` restarts the container. What a user sees:

| Service | Effect of a kill |
| --- | --- |
| app | 502s (Caddy retries for up to `lb_try_duration` 120 s first) until the restarted app has run `prisma migrate deploy` and answers; in-flight requests fail; sessions survive (JWT). |
| worker | the active BullMQ jobs stall and are retried under their attempts; scheduled passes run late; nothing a user sees directly unless a nightly pass misses its window. |
| clamav | scans fail until it is healthy (up to 180 s); a file uploaded meanwhile stays `PENDING`, and in strict AV mode its download is refused until scanned. |
| postgres | every request fails until crash recovery finishes (a killed backend restarts the whole server); pgbouncer reconnects. |
| redis | queued jobs survive (AOF, up to a second of writes lost); enqueues and anything else reading Redis fail for the seconds it takes to reload. |
| caddy | the site is down for seconds; certificates persist in its volume. |
| pgbouncer | every database connection drops for seconds. |
| scanner, egress, proving server | no user-facing effect; a scan or a proving request fails and is retried. |

Before C1 the same exhaustion was host-wide and the kernel chose the victim,
which could have been Postgres for a leak in ClamAV. A limit makes the failure
local to the service that caused it.

**The provisional app and worker limits** are the most likely to be hit: their
peaks were measured with no nightly job. A worker kill during the 02:00–05:30
chain delays that pass (BullMQ retries it); an app kill is a short outage. For
these two, the first thing to give is usually the stated V8 heap (1024 MiB),
not the cgroup: a heap overrun is exit code 134 and `Reached heap limit` in the
container's log, and the restart and retry are the same as for a kill. Watch:

- the `VM capacity` workflow — per-container limit, peak and OOM kills (the
  cgroup's `memory.events`). A peak near the limit with high anonymous memory is
  real; a peak made of page cache is not.
- the `VM check` workflow's `containers` check — restart counts and health. A
  rising restart count on `app` or `worker` with no OOM kill in `VM capacity` is
  a heap abort: confirm with the container's last exit code (134) and its log
  (`Reached heap limit`).

**Follow-up (C1b): re-measure, then tighten.** Dispatch `VM capacity` after
06:00 UTC on a day at least 24 hours after step 3, so every container's peak
spans the full nightly chain. Set `app` and `worker` to about 1.5x their
measured peaks (rounded up, never below 768 MiB), with `--max-old-space-size`
moved in the same diff to about two thirds of each new limit (the guard refuses
anything outside half to three quarters), confirm no heap abort (exit 134) in
the window, confirm ClamAV's peak through a signature reload stays under 3 GiB,
and record the new figures in a note beside this one.
