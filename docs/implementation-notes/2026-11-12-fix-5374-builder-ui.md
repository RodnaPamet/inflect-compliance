# 2026-11-12 — Empty-catalogue cause, and four agent-builder fixes

Issues #5045 and #5374.

## Design

**#5045: an empty catalogue names its cause.** Both reasoning engines settle
`EMPTY_CATALOGUE` when the offered tool set is empty, and both used to write
`EMPTY_TOOLSET_MESSAGE` ("this agent holds no MCP tool grants") whatever the
cause. In production an agent with three granted read tools, whose policy card
permitted none, was told it held no grants. `emptyCatalogueMessage` in
`src/lib/agentic/empty-catalogue-message.ts` now picks the sentence:

- no grants at all: `EMPTY_TOOLSET_MESSAGE`, byte for byte, because
  `ad-hoc-question-result.ts` compares stored rows against it;
- grants, all withheld: `<engine>_no_tools_offered: …`, naming each term and
  the tools it withheld.

The offer's own `omitted` reasons cover scope, autonomy, a read-only connection
or workflow and an unconvertible schema. The grant, the policy card, the
catalogue snapshot and the permission keys are applied inside the candidate
list and leave no `omitted` entry, so the function re-derives them from the
invocation's pinned lists (`grantedTools`, the card's `permittedTools`,
`offeredTools`), which are the same three lists `toolIsLoadable` intersects. The
offer's `PROFILE_TOOL_NOT_GRANTED` is re-read the same way, because the offer
gives that reason for a profile tool the card removed as well as for one never
granted.

**#5374, four builder fixes.**

1. The Behaviour editor posts the starting version's `flow` in place of
   `toolNames` and shows the flow's tools read-only. The save route already
   accepts `flow`, and the usecase checks it as it does on create.
2. `getAgentProfile` reads the newest 50 versions and, when the version in
   force is not among them, reads that one row as well.
3. The Runs tab, the runs list and the run page name a profile run
   "Behaviour v3" / "Behaviour v3 — Test run" through `profileRunLabel`, which
   is built on `parseProfileRunKey`.
4. A Test run of a version that names only propose tools is refused at the
   start (`TEST_RUN_NO_READ_TOOL`, 409). The Behaviour tab disables the button
   with the same reason, from `profileNamesNoReadTool`.

## Decisions

- **No new omission reason inside `offerToolSet`.** Issue #5045 suggested adding
  an `omitted` entry for the policy-card term. Re-deriving it from the
  invocation's pinned lists names the same cause without changing the offer,
  which other work is also changing. It decides nothing: no tool is offered or
  withheld by it.
- **A new code for the new case** (`*_no_tools_offered`) rather than a reworded
  `flue_no_tools_granted`. A reader that matches the old string or its prefix
  keeps meaning "no grants". The run page shows an unknown code as written.
- **The editor keeps the flow and does not edit it.** No surface draws a flow,
  and the save refuses a tool list beside one. Carrying the stored flow
  unchanged is the only edit that keeps it. An integration test shows the flow
  the view returns is accepted as the next version's flow.
- **"No read tool" means "every tool is a propose tool"**, checked against the
  client-safe `MCP_PROPOSE_TOOL_NAMES`. An external tool is a read tool, so
  asking only the propose list counts it correctly.
- **The in-force version is appended, not merged by sort.** It is older than
  every version on the page, so newest-first order still holds. The read stays
  bounded: at most 51 rows.
