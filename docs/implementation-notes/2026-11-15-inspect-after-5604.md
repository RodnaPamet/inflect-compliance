# 2026-11-15 — Inspect after #5604: Flue asks at the questions route; a run that never called the model is not a token-cap FAIL

## Design

Run 43700423641 (agent-evals on main) produced two broken passes.

**Flue.** Every sample was refused `HTTP 400 AD_HOC_QUESTION_USE_QUESTIONS_ROUTE`.
#5604 made `resolveRunDefinition` refuse `ad-hoc-question` on the generic
`POST /agent-runs` for every caller, and allow it only from the ASK trigger
(`startInteractiveRun`, behind `POST /agents/questions`), an `INVOKE_AGENT` rule,
or an A2A delivery. The harness started every Flue sample at the generic route
with the seed agent's bound key.

The questions route is a person's (`resolveInteractiveAgent` refuses a key, an
agent or a job `NOT_A_PERSON`), and the harness already holds the seed OWNER's
session. So the OWNER now asks: `POST /agents/questions` with `{ question }`,
202 `{ runId }`. `startInteractiveRun` binds the tenant's designated interactive
agent to the OWNER's own context, so the reasoning engine still has its ACTIVE
registered agent and the run's tools are still that agent's grants. Two things
the route needs that the harness did not have: the seed designates the Flue
eval agent (`designateInteractiveAgent`), and the workflow sets
`AGENT_INTERACTIVE_RUNS=1`. No product route was widened.

No start path presents a key any more, so the seed mints none (a re-run revokes
an earlier seed's), `--agent-keys` is gone, and the workflow hands the harness
the OWNER's session alone.

Task 10 (missing input) now reads its missing key from the questions route's
own refusal: `AskSchema` refuses `{}` as `VALIDATION_ERROR` with an
`invalid_type` issue on `["question"]` for a value that was not sent.

**Tool Runner.** All seven external runs settled within a second, with no step
and no token ($0 measured spend). Each was dispatched by its rule and logged
`tool-runner: starting a run`, then nothing above info. Reproduced locally on
the same seed and dispatch path with a request the API refuses: the run settles
`FAILED`, `tool_runner_run_failed: <status> {...}`, `stepCount` 0, `costTokens`
0, and logs exactly that one warning. The record's error code is only the
prefix, so the provider's status is not in the record or the job log.

`token-cap-halts-at-the-boundary` scored FAIL on that run: its scorer returned
FAIL for any settlement that was not COMPLETED and not the TOKENS cap, including
a run that never made a model call. A run with no model step and no tokens spent
nothing the cap could be measured against; it is now VACUOUS (NOT_EVIDENCED),
in the Python scorer and the record module alike, with two golden cases (no call
is VACUOUS; a call short of the cap that then failed stays FAIL).

The runner now logs one line per settled run: status, error code, the
provider's HTTP status when an engine's catch-all failure names one, and its
step and token counts. Codes and numbers only.

## Decisions

- The questions route over the AUTOMATION trigger for Flue: #5604 names the
  questions route as the door for the ad-hoc question, and it is the route a
  person uses. The automation path stays the Tool Runner's.
- The token-cap non-vacuity is "a model call happened", not "the cap was
  approached": a run halted by another cap after real calls (`halted by a
  different cap`) stays FAIL, as the golden file already decided.
- The Tool Runner's model is NOT changed here. The workflow pins
  `AGENT_TOOL_RUNNER_MODEL_*` to the budget's model (`budget.json`, D-EV-6),
  and the Tool Runner's locked parameters (`lockedParams`) send adaptive
  thinking, `output_config.effort` and server-side fallbacks, which that model
  does not take. Choosing another model changes the night's cost and the
  record's model revision: an owner decision. The settled-run line names the
  provider's status on the next night.
