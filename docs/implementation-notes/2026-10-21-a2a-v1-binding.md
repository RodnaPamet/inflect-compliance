# 2026-10-21 — the A2A v1.0 binding beside v0.3 (#3866)

J6 of the SAP agent integration roadmap (#3859), the optional phase that makes
"portable" true beyond SAP. SAP's toolkit is on v0.3; a v1.0 host can now call
the same endpoint in its own vocabulary.

**Nothing about v0.3 changed.** That is the whole constraint, and it is checked
rather than asserted: the peer messaging suite verifies signed receipts over
exact response bytes and passes untouched.

## The prompt's claims, all confirmed from source

Every wire claim in the issue checked out at tag `v1.0.1`:

| Claim | Where |
| --- | --- |
| `A2A-Version` header | `specification.md:486`, a standard service parameter |
| Absent header means 0.3 | `specification.md:712` — "except for 0.3 Clients - 0.3 will be assumed for empty header" |
| `TASK_STATE_*` states | `a2a.proto`, `enum TaskState`, 9 values |
| `AgentInterface.tenant` | `a2a.proto`, field 3 |
| `supportedInterfaces` | `a2a.proto`, `AgentCard` field 3, REQUIRED |
| `SendMessage`/`GetTask`/`ListTasks`/`CancelTask` | all four in `service A2AService` |

One of those I nearly recorded as WRONG. My first search for the absent-header
rule covered the service-parameter table, which says nothing about absence, and
I was drafting "the spec does not state this; defaulting to 0.3 is our
decision" when a wider search found line 712 stating it outright. Searching one
section and concluding about the document is the same error as reading one
number and concluding about a population.

## Two things bigger than the prompt described

**1. There is no v1.0 JSON Schema to vendor.** `specification/json/` at the tag
holds only a README saying `a2a.json` is "a **non-normative build artifact**
derived from the canonical proto definition… intentionally **not** committed".
Neither it nor `docs/spec/a2a.json` exists at the tag — both 404.

So J2's approach, vendoring the JSON Schema and walking it with a generic
validator, has nothing to vendor. Generating the JSON needs `protoc` plus
`protoc-gen-jsonschema`, a toolchain this repo does not have.

The proto is vendored instead (blob sha `400cdbad93…`, matching upstream) and
`tests/helpers/proto-messages.ts` reads message fields and their
`(google.api.field_behavior) = REQUIRED` markers out of those bytes. The
property that mattered about the v0.3 fixture holds here too: the constraint
comes from upstream, not from a transcription.

The reader publishes `PROTO_CONSTRUCTS` for the same reason the v0.3 validator
publishes its keyword vocabulary — **the failure mode of a small reader is
blindness**, and a field shape it does not recognise is simply absent from its
output, where it satisfies every "is it required" check by not existing.

**2. v1.0's AgentCard is a different shape, not a renamed one.**

| v0.3 | v1.0 |
| --- | --- |
| `url`, `protocolVersion`, `preferredTransport` | replaced by `supportedInterfaces` (REQUIRED) |
| `securitySchemes`, `security` | `securitySchemes` map, `securityRequirements` |
| `x-inflect`, `x-inflect-signature` | **no `x-` convention exists** |

## Where Inflect's data goes on a v1.0 card

Protobuf JSON rejects unknown top-level fields, so `x-inflect` would make the
card unparseable to a strict v1.0 client. v1.0 does have
`capabilities.extensions[]` — `{uri, description, required, params}` — which is
exactly the mechanism, so the identity, receipt format, signing keys **and the
signature** travel in its params (owner decision, #3866).

Three details that are decisions rather than mechanics:

- **`required: false`, and it is load-bearing.** §3.3.4 obliges a server to
  return `ExtensionSupportRequiredError` when it marks an extension required and
  the client has not declared support. Every v1.0 client in existence is in that
  position, so marking it required would refuse all of them.
- **The URI is a URN** (`urn:inflect:a2a:card-extension:1`). A URI as an
  IDENTIFIER: an https URL invites a fetch of something that is not there, and a
  per-deployment URL would give the same extension a different identity on every
  deployment.
- **The signature stays ours.** v1.0 defines `signatures` expecting JWS over RFC
  8785 canonicalisation. Producing one is a second crypto surface AND a second
  canonicalisation that must agree byte-for-byte with the first or every
  signature is silently wrong. Keeping Ed25519 over `canonicalJson` means ONE
  signing path; an Inflect-aware client verifies it, and a generic v1.0 client
  ignores an extension it does not know, which is what extensions are for.

`signInflectV1Card` is separate from `signInflectAgentCard` rather than a branch
inside it, because that function reads `card['x-inflect']` to check the key it
was handed is the one the card names CURRENT — and the v1.0 card keeps those
keys elsewhere. A branch would have made that check conditional, which is the
half that must never be skipped.

## ListTasks and CancelTask are refused, deliberately

Both exist in v1.0's service and both are refused with
`UnsupportedOperationError`, the spec's own wording for "not supported by this
server agent implementation".

They are not oversights. Each would grant an outside caller authority it has
never had, and **#3866 is a wire binding** — adding authority inside one is how
a binding becomes a feature nobody reviewed.

- **`ListTasks`** enumerates the tasks a caller started: a disclosure surface
  over another organisation's activity in this workspace, with pagination. What
  a caller may see of its own history is the same class of question #3862
  answered for the card, and deserves its own decision.
- **`CancelTask`** lets a remote caller ABORT a run. Aborting is an authority a
  person inside the workspace holds, it stamps the Art 14 outcome, and a run may
  already have queued proposals someone is reviewing.

The streaming and push-notification operations are refused for a reason that
already existed: the card declares both capabilities false, and §3.3.4 REQUIRES
`UnsupportedOperationError` and `PushNotificationNotSupportedError` respectively
when a client uses an undeclared capability.

A test derives the RPC list **from the proto** and asserts every one is either
aliased or explicitly refused — so a future spec adding an operation fails there
rather than falling through to a generic method refusal that tells a conformant
client the wrong thing.

## Three places the peer path was deliberately left alone

The version threads through the SHARED `startInboundRun`, so this took saying
three times:

1. the parser's alias map defaults to `{}`;
2. `taskFor`'s version parameter defaults to `'0.3'`;
3. the peer's `startInboundRun` call omits the field entirely.

The host's call site is anchored on its `HOST_CONSUMER` grant so a string
replace cannot catch both — a match-count assertion caught exactly that during
#3863 and the habit is now the rule.

**The method alias is applied in the parser, never by rewriting the request
body.** `HostConsumerMessage` stores the exact bytes received; a request whose
stored bytes differ from what arrived is not evidence of what arrived.

## TASK_STATE_* is a relabel, not a second opinion

`taskStateForRunStatus` decides what a run's state IS; `v1TaskState` only
re-spells it. A second mapping from run status straight to `TASK_STATE_*` could
disagree with the first, and a caller using only one version would never see the
disagreement.

A consequence worth noting: **`AWAITING_APPROVAL` is `TASK_STATE_WORKING`, not
`TASK_STATE_INPUT_REQUIRED`** — and v1.0 HAS that state, so this is a choice
rather than an absence. #3863's reasoning survives the version change: the
approval can only come from inside the workspace, so naming the caller as the
actor would be as wrong in v1.0 as in v0.3.

## Not done here

- **No pilot.** #3866 offers one against a Microsoft A2A consumer "if access is
  available". There is none, so the binding is proved against the vendored proto
  and our own tests — which is not the same as having been called by a real v1.0
  client. #3866 should stay open for it, exactly as #3865 does for Joule.
- **No streaming, no push notifications, no extended card.** All refused with
  the capability errors the spec names, consistent with a card that declares
  them false.
- **No JWS.** See above; a v1.0 client wanting standard signature verification
  is the trigger to revisit, not before.
