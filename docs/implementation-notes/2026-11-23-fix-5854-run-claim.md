# 2026-11-23 — One run, one executor: the run lease and one job per segment (#5854 finding 2)

**Commit:** `fix(agents): …` (see the branch `fix/fix-5854-run-claim`)

## Design

Finding 2 of the Step 5H adversarial read
(`2026-11-23-step-5h-adversarial-read.md`, questions 2 and 3, "Not fixed" item
2): `agent-run-execute` was enqueued with no `jobId` and `attempts: 3`, and the
`WorkflowRun` row carried no claim. `executeQueuedWorkflowRun` checked only
`status === 'RUNNING'`, which a run a worker is executing also is. So a
stalled-job redelivery, or a retry while the first attempt still ran, executed
one run twice at the same time.

Two independent changes, each closing a different door:

```
enqueue ──► jobId = agent-run-<runId>-<instant of the authorising transition>
             (BullMQ drops a second add of the same segment)

job ──► executeQueuedWorkflowRun
          status RUNNING? ── no ──► skipped NOT_RUNNING:<status>
          claimRunLease ─────────► refused ──► skipped LEASE_HELD | NOT_RUNNING
              │ (UPDATE … SET leaseHolder=<token>, leaseExpiresAt=now()+TTL
              │  WHERE RUNNING AND (no holder OR lapsed))
              ▼
          keepRunLease (renew every 15 s, TTL 60 s, stop at wall clock + grace)
          ctx.runLeaseToken = token ──► executeFrom ──► engine
                                           │  updateRun   … WHERE leaseHolder = token
                                           │  recordStep  … SELECT … FOR SHARE on the token
                                           │  isRunAborted … true if the row names another holder
                                           ▼
                                   lost? ──► RunLeaseLostError ──► skipped LEASE_LOST
          finally: stop renewing, release (… WHERE leaseHolder = token)
```

- **The claim** is one conditional UPDATE on the database's clock: RUNNING, and
  nobody holds the run or the holder's `leaseExpiresAt` has passed. Exactly one
  claimant wins.
- **A worker that cannot claim does nothing** and reports `skipped`, which the
  job logs at INFO and BullMQ does not retry. Before it gives up it watches the
  lease for at most one TTL plus one renewal: a holder that renews is alive
  (`LEASE_HELD`, usually within one renewal interval), and a lease that lapses
  unrenewed was a dead worker's, which the watcher takes over. That keeps a
  crashed worker's run recoverable by BullMQ's own redelivery, which arrives
  15–60 s after a crash, before a 60 s lease could have run out.
- **The token is a fence.** It rides on the executing context
  (`RequestContext.runLeaseToken`), and:
  - `updateRun`, which every settlement and every accounting write goes
    through, matches only the row the token holds and returns `false` (no
    throw) when the run is somebody else's;
  - `recordStep`, the one place a step is written, checks the token with
    `SELECT … FOR SHARE` in the step's own transaction, so a successor's claim
    waits for the write and then reads the ledger with it in; a lost worker
    writes nothing, `alsoInTx` included;
  - `isRunAborted`, the check every reasoning engine already makes where it
    reads the kill switch, reads a run another worker holds (or nobody holds)
    as stopped, so the engine leaves its loop exactly as at an operator's
    Abort. The static driver's between-steps row read does the same.
  - `executeFrom` then sees the lost lease and throws `RunLeaseLostError`
    before any of its settlement steps (operator-abort reconciliation,
    deferral settlement, decision-log stamping, attribution and narrative
    capture), and the worker reports `LEASE_LOST`.
- **Expiry does not fence.** A holder is fenced only when the row names
  somebody else or nobody. A holder whose renewals missed a beat and whom
  nobody replaced renews again and carries on, so the TTL can be short without
  making a slow database a source of stopped runs.
- **The SIGTERM drain** pauses only the rows its own tokens still hold, and
  clears the lease with the pause. The engine still running in that process
  stops at its next check and writes nothing more. Before this it carried on
  and could settle COMPLETED over the PAUSED. A person's resume moves the run
  back to RUNNING and enqueues a job, which claims it.
- **The reaper** treats a live lease as a live executor and an expired one as
  abandoned: it selects (and reaps) a RUNNING run only when its `updatedAt` is
  past the cutoff AND it has no live lease, and it clears the lease it reaps,
  so a wedged holder that wakes is fenced. A holder stops renewing at
  `RUN_LEASE_MAX_HOLD_MS` (the wall clock plus the reaper's grace), so a worker
  wedged in a call that never returns still lapses and is reaped, as before.
- **An operator's Abort still wins** (#5366). `abortWorkflowRun` writes
  ABORTED whatever the lease; the holder reads it at its check, its settlement
  stays off the ABORTED row, and it releases the lease at the end.
- **One job per segment.** `agentRunExecuteJobId(runId, segmentAt)`, built by
  `scheduledJobId`, so the id is colon-free. A start uses the row's
  `startedAt`; a person's resume and a decided deferral use the row's
  `updatedAt` as their #5119 conditional claim left it.

## Decisions

- **A lease on the row, not a re-attach.** Re-attaching to a recorded session
  is Managed Agents-specific and out of scope; the lease is engine-neutral and
  sits in the shared run path.
- **Raw SQL for the lease statements.** The database's `now()` decides expiry,
  so hosts with skewed clocks agree. Raw SQL also writes no hash-chained audit
  row for a renewal every 15 s and leaves `updatedAt` alone, which the reaper
  reads as "last progress".
- **Inline runs take no lease.** A static start or resume walks in the request
  and is not delivered by BullMQ; with no token every fence is a no-op and
  adds no query, so those runs and every unit test of an engine behave as
  before. A queued run the static engine walks (a tenant switched engine after
  the enqueue) does carry a lease, and the static driver honours it.
- **Watching instead of failing fast.** The brief's rule is "a worker that
  cannot claim does nothing". Taken literally with a 60 s TTL, BullMQ's
  redelivery of a crashed worker's job would arrive while the dead lease was
  still live and the run would wait an hour for the reaper. Watching for one
  TTL keeps today's crash recovery, costs a duplicate delivery at most one
  renewal interval while the holder is alive, and still never executes.
- **The jobId names the authorising transition, not a counter or a clock
  read at the enqueue.** A run can park twice at the same `stepCount` (a guard
  FLAG writes no step), so a counter would reuse an id BullMQ still holds among
  its completed jobs and the resume would be silently dropped. A `Date.now()`
  at the enqueue would make two enqueues of one segment differ, which is the
  duplicate the id exists to refuse.
- **What a lost worker can still do.** Between the moment it loses the lease
  and its next check, a worker can finish the ONE call it has in flight: a
  model call (its decision-log row is still written, which is true: the call
  was made) or a tool call (a proposal it queues is queued). It writes no step
  and no settlement for it. Fencing every tool call on the token is item 3's
  question, below.
- **Managed Agents.** A lost worker's `finally` still deletes its session at
  Anthropic; the `SESSION_DELETED` ledger step is fenced like any step, so the
  reconciliation's abandoned-session pass reads the session as abandoned,
  finds it gone (404) and records the deletion.

## Not done: resume rather than re-run (item 3)

The brief's minimum was: a tool call recorded DONE in the ledger for this
segment must not be executed again on a retry. For the **static engine** that
already holds: `executeQueuedWorkflowRun` resumes at
`max(ledger max seq + 1, stepCount)`, and each step is one declared call.

For the **reasoning engines** (Flue, the Tool Runner, Managed Agents) it does
not, and it cannot be made to hold without a decision:

- A retry starts the engine again from the opening message (`runMessage` takes
  no offset, #5372), and the model chooses its calls afresh. Nothing maps a
  call the model asks for now to a call a dead attempt made.
- The ledger cannot replay a DONE call: a `TOOL_CALL` step stores the model's
  ARGUMENTS and never the RESULT (`tool-runner/tools.ts`: "the result is tenant
  content"). There is nothing to hand back instead of executing.

Options, each needing an owner decision:

1. **Store results and replay.** Persist each DONE call's result (encrypted,
   Epic B manifest) and, on a retry, answer an identical call (tool name and
   canonical arguments) from the ledger instead of executing it. New storage
   of tenant content per step; "identical" is a judgement (a model may
   legitimately call `list_risks` twice); the replayed result may be stale.
2. **Persist the transcript and resume it.** The deferral resume (Step 2f)
   already stores an encrypted transcript and continues it; doing that at
   every turn would let a retry continue the conversation where it stopped.
   New storage of model text per turn, and a byte-faithful continuation (a
   thinking block's signature binds it).
3. **Refuse a repeat of a non-idempotent call.** On a retry, refuse a propose
   tool or an external write whose canonical arguments match a DONE step of
   the run, answering the model with a refusal. Read tools re-run harmlessly.
   Changes what the model sees on a retry; needs the proposal digest or the
   external write journal as the identity.
4. **Do not auto-retry a reasoning segment that already called a tool.** A
   retry that finds a `TOOL_CALL` in the ledger after the segment's start
   parks the run PAUSED for a person's resume (as the SIGTERM drain does)
   instead of re-running it. Simplest; trades automatic recovery for a person.

This branch implements the two concurrency changes only.
