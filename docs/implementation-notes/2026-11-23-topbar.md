# 2026-11-23 — Phone top bar: assistant and search entry points, shell gaps, chrome tap targets

Mobile roadmap Phase 1, items 4, 11 and 12 (#5813, #5820, #5821).

## Design

**Two phone-only entry points, through a slot.** The top bar's right slot now
takes host-supplied icon buttons:

```
tenant layout (server)                 AppShell (client)      TopChrome
  topBarActions={                  ──▶   topBarActions   ──▶   actions
    <CommandPaletteTopBarButton/>                             [switcher][search][assistant][bell][avatar]
    <AssistantTopBarButton/> }
```

`TopChrome` and `AppShell` are shared UI (`docs/_status/ui-core-classification.json`
records `TopChrome` GENERIC), and the palette and the assistant are product
modules, so the layouts that already own those modules supply the nodes rather
than the chrome importing them. The org layout supplies the search button only;
the assistant is a tenant-layout feature.

Both buttons are `md:hidden` and use `NAV_BAR_ICON_BUTTON_CLASS`, the
hamburger's recipe hoisted into a named export: 22px painted, 44px on a coarse
pointer.

**One assistant sheet.** `AssistantLauncher` still mounts the sheet, once. The
floating button's wrapper is `hidden md:block`; the top-bar button writes the
shared open state in `assistant-open-context.tsx` and renders only while
`available` is true, which the launcher sets only when its own gate passes
(kill switches, `canWrite`, not on `/t/<slug>/auth/*`). So the icon, the
floating button and the palette entry read one gate. The context gained
`returnFocusRef`: the top-bar button records itself when it opens the sheet,
and the launcher's close focuses it instead of its own button, which is
`display:none` on a phone.

**Search.** `CommandPaletteTopBarButton` calls `useCommandPalette().open` — the
one palette `providers.tsx` mounts.

**Shell gaps.** The drawer's heading defaults to `mobileNav.drawerTitle`
("Navigation" / "Навигация") instead of the hamburger's "Open navigation
menu". The toaster moved into `AppToaster`, which reads `useTheme()` and
switches `position` on the viewport width: `bottom-center` below 768px,
`top-right` from there up, with a `mobileOffset` bottom that adds the
home-indicator inset.

**Tap targets.**

| control | painted | on a coarse pointer |
| --- | --- | --- |
| brand link | 22x22 mark | link `min-h-11 min-w-11`, mark unchanged inside it |
| bell | 22x22 | `min-h-11 min-w-11`; badge moved in by the 11px it gained |
| search, assistant icons | 22x22 | `min-h-11 min-w-11` (shared recipe) |
| record pager chevrons | 16x14 each | each `min-h-11 min-w-11`, laid out in a row |
| `InfoTooltip` | 16x16 | `TOUCH_HIT_AREA_CLASS`: a centred `::after`, at least 44x44 |
| `Checkbox` | 16/20/24 | unchanged: `globals.css` already gives `[role="checkbox"]` a 44px `::before` on coarse pointers |

**Tooltips on tap.** `Tooltip` is now controlled. On a `pointerdown` whose
`pointerType` is touch or pen followed by a click, it toggles open, when
`openOnTap` is true or, by default, when the trigger is not itself a link or
control and sits inside none. `InfoTooltip` passes `openOnTap`. A tap outside
closes it through Radix's own dismissable layer. Mouse and keyboard behaviour
is unchanged.

## Decisions

- **A slot, not an import, for the top-bar buttons.** Importing the palette or
  the assistant into `TopChrome` would add a `domain-import` coupling to a file
  recorded GENERIC and fail `ui-core-classification`. The tenant layout already
  owns the assistant's kill-switch read, so it is the natural host.
- **The icon reads `available`, it does not re-derive the gate.** Same rule as
  the palette entry (#3840): one gate, one reader. Suppressing the launcher on
  the auth gate therefore removes all three entry points at once.
- **Bottom-centre toasts by viewport width, not CSS.** `sonner` takes one
  `position` per Toaster and has no per-breakpoint form; two Toasters would
  split one toast stream. Until the width is known the desktop position
  applies, and `sonner` renders no toast before then.
- **The pager goes horizontal on touch rather than wearing pseudo-element hit
  areas.** Two stacked 44px targets make an 88px column that doubles the title
  row; pseudo-elements reaching 30px above and below would overlap the back
  link and the tab bar and answer for their taps. A row keeps the title line at
  44px. The chevron glyphs are unchanged.
- **The brand mark moved inside the link.** The gradient square was the link
  itself, so the hamburger's `min-*` floor would have painted a 44px brand. A
  pseudo-element hit area would have overlapped the 44px hamburger by 3px.
- **Tap-to-open is opt-in for action buttons.** Tooltips sit at `z-[99]`, above
  sheets and modals; opening one on every icon-button tap would leave a label
  floating over whatever the button opened. The default opens only for triggers
  with no action of their own, and the `closest` check keeps a badge inside a
  row link from cancelling the link's navigation.
- **The checkbox needed no change.** Its 44px hit area on coarse pointers
  already comes from the `[role="checkbox"]::before` rule in `globals.css`
  (mobile PR-1). An audit that measures `getBoundingClientRect` reports it as
  16px because a pseudo-element is not part of the box; `elementFromPoint`
  shows the real hit area.
