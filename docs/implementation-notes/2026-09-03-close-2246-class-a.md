# 2026-09-03 — #2246 Class A: mask comments at the read seam

**Commit:** `<pending> test(guardrails): close #2246 Class A — mask comments at the read seam`

## Design

Class A of #2246 is one sentence: *a test file reads source text and asserts
against it without masking comments, so a COMMENT satisfies an assertion meant
to be about CODE.* The failure mode it enables is the "delete the code, keep the
note explaining it" diff — green.

The fix is applied at the **read seam**, not per assertion:

```ts
// before
const read = (rel: string) => fs.readFileSync(path.join(ROOT, rel), 'utf8');
// after
const read = (rel: string) => codeOf(fs.readFileSync(path.join(ROOT, rel), 'utf8'));
```

`codeOf` (`tests/helpers/source-blocks.ts`) blanks comments to **spaces** and
leaves string literals and newlines alone, so byte offsets and line numbers are
unchanged and every existing `\s*` in a needle still matches. Every assertion
below the seam is covered, and so is every assertion added later — which is the
property per-assertion wrapping does not have.

Three seams are deliberately **left raw**, and the distinction is the whole
reason this was not a blind sweep:

| read | masked? | why |
| --- | --- | --- |
| `.ts` / `.tsx` / `.prisma` source | yes | `//` is a comment |
| `.md` / `.yaml` / `.json` | **no** | `//` is content — the `https://` of a URL. Masking would delete real text |
| `.sql` migrations | `maskSqlComments` | `codeOf` lexes TypeScript and does not know `--`; a blind wrap reads as covered while catching nothing |

### The analyser had to learn the mask, or the fix would have paid a ceiling

`tests/helpers/assertion-reach.ts` backs both #2246 ratchets. Before this
change it treated `codeOf(readFileSync(…))` as a transform it could not follow
— `content-transformed`, a **capped** skip — and the hoisted form
(`const read = (p) => codeOf(readRaw(p))`) it did not recognise as a file read
at all, landing those sites in `not-a-file-read`, which is **uncapped**.

So the conversion would have either pushed a ceiling up by roughly the number
of files converted, or moved ~900 assertion sites out of the population
silently. The fix for one defect class paying a ceiling to the detector for
the other. The analyser now follows a comment mask — inline, hoisted into the
read helper, delegating to a sibling reader, or rebuilt from a LOCAL
`.replace()` stripper's own source — and counts satisfying positions against
the **masked** text.

Following the mask is strictly *more* accurate, not a loosening: a needle whose
extra matches were all inside comments was never ambiguous. The mask is taken
from the DEFINITION, never from the identifier — an unimported `codeOf` stays
in the capped bucket, because applying the shared mask on the strength of a
name would be measuring text no assertion ran against, i.e. the detector
committing the defect it exists to find.

### What masking exposed

Ten assertions went red the moment comments stopped counting. **Every one of
them had been green on prose** — that is the finding, not a side effect of it.
Eight were re-anchored on what the code actually satisfies; each re-anchor was
then mutation-proved by deleting the real construct from the source and
confirming the assertion is the SOLE test in its file that fails.

Two were not re-anchorable, because the thing they named does not exist in
code anywhere — see Decisions.

## Decisions

- **The DSAR pair is a real defect and was NOT re-anchored.**
  `dsar-workflow-coverage.test.ts` asserted `/userId\s*=\s*NULL/i` and
  `/NOT deletion|not delet/i` against `src/app-layer/jobs/dsar-erasure.ts`.
  Both phrases live *only* in the JSDoc of `eraseUser`, and that module is a
  Stage-1 stub whose body is a single `throw`. So the GDPR invariant "audit
  rows are pseudonymized, not deleted" has never been enforced by anything.

  Measured, not inferred: with the guard exactly as it stood on main (raw read,
  both prose needles) and `eraseUser` replaced by an implementation whose body
  is `prisma.auditLog.deleteMany({ where: { userId } })` — the precise thing the
  invariant forbids — the suite is **7/7 green**.

  Weakening the needle would keep that hole open, so the guard now asserts the
  truth about today: `eraseUser` still returns `Promise<never>` and still
  throws. It goes **red the day somebody implements erasure**, which is the
  moment the real behavioural invariant can be written and the only moment
  anyone will be in a position to write it. This needs a tracking issue against
  the Stage 3 PR.

- **A ratchet baseline that a conversion improves must be re-seated in the same
  diff.** `DRIFT_ALLOWANCE` is 0 in both #2246 ratchets, so a baseline sitting
  above the live count is headroom the next regression spends with a green
  build. Class D moved down on all three counts. Class C did not move at all
  and its file is untouched — Class C measures the shape of the regex, not the
  text it runs against, so comment masking cannot affect it. An unchanged
  number here is a result, not an omission.

- **The un-analysable drop (1507 → 1447) is a real shrink, not a re-label.**
  102 sites left `content-transformed` and became analysed. In the same pass
  `path-not-constant` rose 901 → 913, because a masked read whose path comes
  from a loop variable now gets far enough to be classified by its PATH rather
  than dropping out one step earlier. Both directions are the accounting
  getting more accurate.

- **Two guards were bound to a construct rather than having their needle
  narrowed.** The NIST privacy and SSDF seed guards both read the whole of
  `prisma/seed.ts`, and `provider: 'NIST'` is satisfied by either NIST block.
  Narrowing the needle was not available: the public-domain notice they assert
  is written as two adjacent string literals (`'… considered public ' +
  'information …'`), which no character class can cross — which is why the
  original needle only ever matched the banner COMMENT above the block. Binding
  to `declarationOf(seed, 'nistPrivacyMeta' | 'nistSsdfMeta')` fixes both the
  reach and the ambiguity, and takes the sites out of Class D's population
  entirely, because narrowing is the fix that ratchet asks for. Proved by
  cross-check: deleting the copyright from the SSDF block reddens the SSDF
  guard and leaves the privacy guard green, and vice versa.

- **Two hand-proved Class D instances needed their line numbers moved, not
  their counts.** `audit-s5-readiness-scoring.test.ts:21/22` became `:24/25`
  because the conversion added three lines above them. The occurrence counts
  (3 and 2) are unchanged — all three `frameworkKey String` and both
  `auditCycleId String?` are real fields. That positive control is the only
  thing in the ratchet that would notice the analyser quietly ceasing to
  resolve a site, so it is worth its maintenance.

- **A localized string cannot be asserted in the component.** Three org-widget
  guards matched English prose (`may be stale`, `at risk`) that exists only in
  their file headers — the rendered text is `t('widgets.maturityStale')` and
  lives in `messages/`. The re-anchor names the conditional and the i18n key,
  which together *are* the note. This is a general trap for any guard written
  against a component that was localized after the guard.
