# 2026-11-12 — #5376 part C: traceability view keys, trashed controls on risk pages, Risk Register owner and control labels

**Commit:** `fix(traceability,risks,reports): reads honour each side's view key; risk pages hide trashed controls; register owner and code-first controls (#5376)`

Three product changes the owner decided on #5376 on 2026-11-12. Part A is #5424,
part B is #5427 (which added the tests this part flips).

## Design

**1. Traceability reads answer to each entity's own view key.** The reads in
`usecases/traceability.ts` (six `list*` panels, the control / risk / asset /
policy `get*Traceability` views) gated on the coarse read tier alone, so a
custom role without `risks.view` read risk titles through a control's panel,
while the graph over the same links (`traceability-graph.ts`) already dropped
them. Each read now decides per side:

```
anchor (the entity in the URL)   not viewable → 403 (route: requirePermission + AUTHZ_DENIED;
                                                     usecase: assertCanRead<Entity>)
each linked kind                 not viewable → [] and its query is not run
```

The routes take the anchor's view key — the key that entity's own detail GET
already takes (`GET /risks/:id` is `risks.view`, and so on) — so a refusal
writes the hash-chained `AUTHZ_DENIED` row the same way. The usecase asks the
same anchor again, as a floor for any caller that is not a route. Omission
reuses the policies' boolean twins (`canReadControls`, and the new
`canReadRisks` / `canReadAssets`). The policy view reads its controls even when
they are hidden from the caller, because they are the path to the inherited
risks and assets; only the output drops them.

**2. Risk pages hide controls in the trash.** Soft-deleting a control keeps its
`RiskControl` rows, and the soft-delete extension filters top-level reads only.
The risk list's select (whose `controls.length` is the Controls column), the
risk detail read (`RiskRepository.getById`) and the risk's traceability panel
(`ControlRiskRepository.listByRisk`) now carry `control: { deletedAt: null }`,
the predicate the Risk Register PDF took in #5427.

**3. Risk Register PDF.** Owner is the named `treatmentOwner`, else the assigned
user (`ownerUserId`) shown as the risk list shows them — `ownerDisplayName`,
the name, else the e-mail's local part — else "Unassigned". `Risk` has no
relation to `User`, so the names come from one batched read
(`ReportRepository.getOwnerUsers`). Controls read code first: `annexId`, else
`code`, then the name; the name alone when neither exists.

## Decisions

- **Refuse the anchor, omit the rest.** Refusing the whole read when a linked
  kind is hidden would break a control's page for a role that may see controls
  but not risks; omitting the anchor would answer an empty panel indistinguishable
  from "nothing linked". The graph already skips per kind; this is the same rule.
- **`assertCanReadRisk` changed in place.** It had no production caller and its
  name already says "view risks"; it now asks the key every built-in reader
  holds, so its unit test is unchanged.
- **Code precedence is `annexId`, then `code`.** The register has always printed
  `annexId`; keeping it first means no existing row changes its identifier, and
  `code` fills the gap for custom controls. The evidence export uses the same
  order.
- **The assigned user reads like the risk list, never as a full e-mail.**
  `ownerDisplayName` is the shared helper for owner columns.
- **Left alone, deliberately:** `coverageSummary` (the coverage dashboard, also in
  `traceability.ts`) still gates on the coarse tier and lists risk titles, asset
  names and control names; the owner's decision named the traceability panels.
  The residual-score suggestion on the risk page still counts trashed controls,
  and an asset's linked controls (`AssetControlRepository.listByAsset`) still
  show them; the decision named the risk page's linked controls and the list
  count. Each is left for an owner decision rather than changed here.
