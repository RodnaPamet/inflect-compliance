# 2026-11-12 — Risk Register drops controls in the trash (#5376, part B)

## Design

Part B of the #5376 coverage gaps added behavioural tests for the concurrent-run
cap setter, `get_agent_recertification_evidence` through `/api/mcp`, the
calendar's time-zone arithmetic, `getReports`, and the traceability reads. One
of them found a defect.

The Risk Register PDF (`getReports` → `ReportRepository.getRiskRegisterData`)
already drops soft-deleted RISKS, with a comment explaining why: a soft delete
says the row is no longer part of the register. Its CONTROLS column did not
apply the same rule one join down. Soft-deleting a control keeps its
`RiskControl` rows (so a restore brings the mapping back), and the soft-delete
query extension injects `deletedAt: null` into top-level reads only, never into
a nested `include`. So a control in the trash was still printed as mitigating
the risk.

The fix is a nested `where: { control: { deletedAt: null } }` on the
`controls` include — the same predicate the coverage and readiness joins use.

## Files

| File | Role |
| --- | --- |
| `src/app-layer/repositories/ReportRepository.ts` | Filters linked controls in the trash out of the register's controls column. |

## Decisions

- **Fixed in the report only.** The risk detail page (`RiskRepository.getById`)
  and the risk list's controls select have the same nested-include shape and
  also show a control in the trash. Those are interactive surfaces where
  showing a linked-but-trashed control may be wanted (to restore or unlink
  it), so changing them is a product decision and is reported rather than
  made here. The PDF is an attestation an auditor reads, and its own
  repository already states the rule.
- **The join row is not deleted.** Unlinking on soft delete would make a
  restore lose its mappings; filtering at the read keeps both.
- Everything else part B tested matched the code's intent and was pinned, not
  changed: the traceability reads' coarse `assertCanRead` gate (raised as an
  owner question), the report's `treatmentOwner`-only owner column, and its
  `annexId`-else-name control label.
