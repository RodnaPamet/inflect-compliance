# ISO/IEC 27001:2022 Annex A fixture — provenance

`iso27001_2022_annexA.json` in this folder is **original work by Inflect**,
keyed to ISO/IEC 27001:2022 Annex A control identifiers. It is not imported
third-party content, and nothing in it is redistributed under anyone else's
terms.

## What was taken from the standard, and what was not

| field | provenance |
|---|---|
| `key` | ISO/IEC 27001:2022 Annex A **control identifier** (`5.1` … `8.34`), reference only |
| `theme` / `themeNumber` | Annex A's four theme names and their clause numbers, reference only |
| `sortOrder` | The identifiers' own numeric order |
| `title` | **Inflect's own prose.** An obligation statement naming the outcome the control requires. |
| `summary` | **Inflect's own prose.** A paraphrase of what the control asks for. |

**No ISO text is reproduced.** Not control titles, not control text, not
implementation guidance. The identifiers and theme names are references — the
same basis `ai-governance-self-assessment.json` already states for ISO/IEC
42001:2023 in this folder: *"clause references only — © ISO/IEC"*.

ISO/IEC 27001:2022 is © ISO/IEC. A copy is purchased from ISO or a national
member body; nothing here substitutes for it, and a tenant implementing these
controls needs the standard itself.

## Why this file exists

`#3478`, found while scoping the Flue skill corpus (`#3470`). Every other
derived fixture in this folder carries provenance — six have `source` /
`license` / `attribution` keys and two ship a sibling `LICENSE.md` — and this
one carried none, while being demonstrably keyed to a published standard. The
gap was not a claim that the file infringed anything; it was that **the file
made no claim at all**, so a reader could not tell whether the question had
been asked and answered or never asked.

## How the titles came to be ours

Owner decision, 2026-10-15: regenerate from identifiers only.

Before that decision the `title` field held ISO's control titles verbatim
(`5.1` → "Policies for information security"). Reproducing short factual
control titles alongside original paraphrase is ordinary industry practice and
was very likely fine — but "very likely fine" is not a provenance claim
somebody can record, and deriving a Flue skill from a source that declares
none would have meant **inventing** one, which is worse than the gap.

So the titles were rewritten as **obligation statements** rather than topic
labels. That is a deliberate change of grammatical form, not a thesaurus pass:
ISO's titles are noun phrases naming a subject, and a noun phrase naming the
same subject is exactly what collides. An outcome statement cannot.

    5.1   Policies for information security
          → Security policy set approved and kept current
    8.10  Information deletion
          → Data erased once its retention basis ends
    8.11  Data masking
          → Identifying values obscured outside need-to-know

**The accepted consequence:** tenant-visible control titles changed. The
identifier is the stable key — `FrameworkRequirement` is upserted on
`(frameworkId, code)` and every mapping, template and piece of evidence joins
through the code or the row id — so nothing was orphaned. What changed is the
words beside the number, and they are now ours.

## What keeps this claim true

`tests/guardrails/catalog-requirement-prose.test.ts` asserts it rather than
trusting this file:

- no fixture `title` reproduces a known Annex A control title, by equality or
  by containment, over a sample of real titles drawn from across all four
  themes;
- the 93 titles are distinct from one another;
- this provenance file exists and names the standard it references.

A convenience paste of a real title — the way this would most plausibly
regress, when somebody "corrects" a title to match the standard a customer
quoted — turns that suite red.
